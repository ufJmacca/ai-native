## Red

The phase captured independently executable failures before each production
slice:

- missing `build_identity` and `release_receipt` modules failed collection;
- the wheel lacked an embedded package identity and outputs did not consume one
  shared identity;
- the clean-wheel harness lacked alternate-interpreter support and then exposed
  five exact golden-tree identity drifts;
- the absent OCI context, Dockerfile, and runtime contract produced five
  failing image tests;
- missing compatibility and certification-schema modules failed collection;
- the missing offline verifier and receipt builder failed their focused
  suites;
- the absent release workflow and automated draft-release progression failed
  the static automation contract;
- the absent pre-merge factory-runner workflow failed three CI contract tests;
- local-runtime compatibility initially accepted no source-bound runtime tag,
  and the first tightening test proved its Docker image ID was not yet bound to
  the certified digest; and
- the missing runbook and Make targets failed all three release-documentation
  tests.

These failures represented missing behavior or explicit contract drift, not
authentication or dependency assumptions.

## Green and security refactor

Notable production behavior:

- `FactoryRunnerBuildIdentity` is the one identity source for packaged
  resources, outputs, evidence, compatibility reports, image labels, and
  receipts.
- The custom Hatch hook generates the wheel resource in a temporary build
  directory and never rewrites the source checkout.
- The compatibility and receipt contracts use strict Pydantic validation,
  canonical RFC 8785 bytes, digest-pinned image references, fixed repository
  identities, passed-only status, duplicate-key rejection, and generated
  Draft 2020-12 schemas.
- The offline verifier rejects unsafe asset names, symlinks, races, oversized
  inputs, malformed or hostile ZIP members, duplicate archive members,
  metadata drift, missing identity/schema resources, digest drift, and receipt
  or compatibility cross-binding failures.
- The OCI build copies only the exact wheel, lock metadata, and a pinned uv
  binary stage. The runtime has no source tree, credentials, ports, volumes, or
  Docker/GitHub client, and runs as fixed non-root.
- Pre-merge CI has `contents: read`, performs no login, push, attestation, or
  publication, and cryptographically binds its source-scoped local Docker image
  ID to the digest used by the strict report.
- The release workflow receives only its job-scoped GitHub token. It does not
  inherit the long-lived Release Please token.
- Every external action used by every checked-in workflow is pinned to a full
  40-character commit.
- Release Please creates an exact-tag draft, and only the receipt-resolved
  clean-download and attestation gates may publish it.

## Automated release and handoff

The AN-04 phase PR may merge only after the existing `test` and `lint` checks
and the new `factory-runner-ci` check succeed on the exact head. Repository
policy requires zero approving human reviews. The trusted CLI controller
revalidates the exact head, base, evidence, and checks, submits one SHA-bound
normal merge, and observes the resulting default-branch commit without an
administrative bypass or native auto-merge.

After GitHub reports the AN-04 merge, Release Please updates its own protected
release PR. The same trusted controller evaluates and merges that generated PR
through the exact-head CLI gate. After the observed merge, Release Please
chooses the actual version and creates the exact tag plus a draft release. The
release remains draft unless wheel/image compatibility, vulnerability, SBOM,
provenance, receipt, clean-download, and independent attestation verification
all pass.

The release initially supports `linux/amd64`. Consumers use only the wheel URL
and the digest-pinned
`ghcr.io/ufjmacca/ai-native-factory-runner@sha256:...` identity recorded in the
published receipt; no mutable image tag is required.

FF-00 remains blocked until automation observes the published release,
downloads and independently verifies its formal receipt and referenced
artifacts, and records the actual semantic version, source SHA, wheel digest,
OCI digest, schema digests, compatibility report digest, and attestations.
